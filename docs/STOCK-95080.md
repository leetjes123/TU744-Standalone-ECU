# Stock M95080 and main-flash calibration

The `stock-95080` profile retains the full schema-4 calibration in RAM and main
NOR flash. Build with `python firmware/tu5jp_standalone/tools/build.py stock-95080`.
The output-enabled experimental image and source/hash manifest are in
`build/stock-95080/`. Default Keil/uVision and `engine-experimental` builds still
use the earlier 8192-byte EEPROM layout. Select the stock profile explicitly.

| Storage | Byte range | Contents |
|---|---|---|
| NOR | `50000..5FFFF` | Tune slot 0: 32-byte header + 3072-byte tune |
| NOR | `60000..6FFFF` | Tune slot 1: same layout |
| M95080 | `000..31F` | One full 800-byte OEM-format history snapshot |
| M95080 | `320..37F` | Standalone DTC journal slot 0 |
| M95080 | `380..3DF` | Standalone DTC journal slot 1 |
| M95080 | `3E0..3FF` | Unused |

The [ST M95080 datasheet](https://www.st.com/resource/en/datasheet/m95080-w.pdf)
specifies 1024 bytes with 32-byte write pages. This profile rejects EEPROM accesses
beyond 1024 bytes. The complete 768-byte OEM-format history payload and 32-byte
envelope fit once. CRC/commit detects a torn write but cannot recover its previous
snapshot. The smaller standalone DTC journal retains two copies. This standalone
allocation does not claim to reproduce the OEM EEPROM layout.

The [AMD Am29F400B datasheet](https://www.batronix.com/files/Datenblaetter/29__/AM29F400B.pdf),
sector tables 2/3, gives both BB and BT variants full 64 KiB sectors at `50000`
and `60000`. The stock linker excludes everything at or above `50000`; its
512 KiB image leaves both slots erased. No suffix-specific boot-sector erase
is used. The driver assumes the existing project's x16 Am29F400B-compatible bus
and command set; it does not identify arbitrary flash chips.

Save requires valid calibration, no staging transaction and stopped operation.
It latches service mode and cancels outputs. The save-accepted reply drains
before erase. A position-independent assembly worker is copied to external SRAM,
verified and called with a C166 code pointer. Interrupts are masked while flash
is busy; the worker services the watchdog and polls DQ7/DQ5. Software timeout
requests CPU reset from SRAM instead of returning into busy flash. Physical
reset/flash wiring remains unverified. Read-only status requests lost during
erase may be retried; the host does not automatically repeat the save command.

The inactive sector is erased, written and verified before its commit word is
programmed. Boot validates header/payload CRCs, schema, all calibration fields
and sequence numbers, selecting the newest valid slot. Missing/unreadable
calibration leaves start inhibited, with no default tune. The previous valid
flash tune survives incomplete writes to the other slot. Successful save requires
reset before operation. There is no automatic flash save per edit or at key-off.

See [the plugin guide](../tunerpro/README.md) for TunerPro. Read-only command `2D`
reports the storage layout. This change does not establish OEM diagnostic parity,
decoder equivalence or engine acceptance. The supplied Bosch training PDF page 13
provides functional context for retaining faults/adaptives during power latch;
it does not establish this journal layout or prove physical power release.

Verification covers interrupted flash-program prefixes, EEPROM bounds/pages,
linked C167 execution of the RAM worker against an AMD command model, engine
outputs and plugin transactions against the actual firmware parser. Physical
flash timing, brownout behavior and TunerPro RT/adapter interoperability remain
hardware acceptance work.
